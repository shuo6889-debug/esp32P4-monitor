## 0. 三分钟速览

| 项目 | 内容 |
|---|---|
| 一句话 | 把 ESP32-P4 开发板做成一款「自己发 Wi-Fi 热点、手机浏览器打开就能看」的实时摄像头 |
| 效果 | 手机连上 `WAVESHARE-P4`，浏览器打开 `http://192.168.4.1`，看到 800×640 的实时画面 |
| 主控 | ESP32-P4（RISC-V 双核，**芯片内没有 Wi-Fi 射频**） |
| 网络 | 靠板上另一颗 **ESP32-C6** 当网卡，P4 与 C6 之间是 SDIO，软件层用 **ESP-Hosted** 打通 |
| 摄像头 | OV5647（树莓派 Camera B 模组），**MIPI-CSI** 接口，2 条数据 lane，每 lane 200 Mbps |
| 采集格式 | RAW8、800×640、50fps（传感器能力；实际推流帧率受编码与网络限制） |
| 图像处理 | CSI 采 RAW8 → **ISP** 转 RGB565 → **JPEG 硬件编码器**压缩（质量 70） |
| 传输方式 | HTTP `multipart/x-mixed-replace`（即 MJPEG 流），浏览器原生支持，不需要写 JS |
| 代码规模 | 应用逻辑 **1 个文件 375 行**（`main/main.cpp`），其余是配置与第三方组件 |
| 内存占用 | 自己申请的大块内存约 **4.2 MB**（2 帧采集缓冲 + JPEG 输出缓冲），必须靠 PSRAM |
| 框架 | ESP-IDF **6.1.0** + FreeRTOS |

**这个项目最反直觉、也最值得先记住的一件事**：ESP32-P4 没有 Wi-Fi。所有 `esp_wifi_*` 调用
之所以能工作，是因为 `esp_wifi_remote` 组件把调用转发给了 C6（第 4.6 节详述）。

## 1. 它到底在做什么：一条数据流水线

理解下面这条线，就理解了这个项目 80%。左边一列是「谁干的」，右边是「数据形态」。关键是要看清
**哪些步骤是硬件自动完成的（CPU 不参与）、哪些是软件任务在跑**，以及**数据在哪块内存里**。

```
  OV5647 摄像头模组
      │
      │ ① 物理链路：MIPI-CSI，2 lane × 200Mbps，24MHz 输入时钟
      ▼
  ┌─────────────────────────────────────────────────────────────┐
  │ ESP32-P4 CSI 控制器（全硬件，CPU 不参与）                      │
  │ ② 把串行像素流还原成 RAW8，用 DMA 直接写进 PSRAM               │
  └─────────────────────────────────────────────────────────────┘
      │ 写完一帧 → 触发中断 → camera_trans_finished() 把缓冲区指针丢进队列
      ▼
  PSRAM 中的帧缓冲区 A / B（各 1 024 000 字节 = 800×640×2）
      │  双缓冲轮换：一块在拍，另一块在处理
      │
      │ ③ camera_task 收到队列消息 → esp_cache_msync() 让 CPU 看到 DMA 写的新数据
      ▼
  ┌─────────────────────────────────────────────────────────────┐
  │ ISP 图像信号处理器（硬件）                                     │
  │ ④ RAW8（拜耳原始数据）→ 去马赛克/白平衡/色彩转换 → RGB565        │
  │    原地转换：结果直接覆盖回同一块缓冲区                          │
  └─────────────────────────────────────────────────────────────┘
      │
      │ ⑤ camera_task 拿着锁，把这块 RGB565 交给 JPEG 编码器
      ▼
  ┌─────────────────────────────────────────────────────────────┐
  │ JPEG 硬件编码器（硬件）                                        │
  │ ⑥ RGB565 → JPEG，质量 70，YUV422 色度采样                      │
  └─────────────────────────────────────────────────────────────┘
      │
      ▼
  s_jpeg_buffer（PSRAM 里约 1.04 MB）＋ s_frame_number 帧号递增
      │
      │ ⑦ httpd 任务里的 stream_handler()：持锁 memcpy 出一份 → 放锁 → 慢慢发网络
      ▼
  HTTP 响应：Content-Type: multipart/x-mixed-replace; boundary=frame
      │  每个分段 = "--frame\r\nContent-Type: image/jpeg\r\nContent-Length: N\r\n\r\n" + JPEG 裸数据
      ▼
  手机浏览器里的 <img src="/stream">：浏览器自动用新帧替换旧帧 → 看起来就是视频
```

### 谁在跑：四个执行体

| 执行体 | 代码位置 | 干什么 | 关键约束 |
|---|---|---|---|
| CSI 中断（ISR） | `camera_get_buffer`、`camera_trans_finished` | 只做「发缓冲区、把完成的帧丢进队列」 | **必须 `IRAM_ATTR`**；只准用 `...FromISR` API；绝不能做耗时操作 |
| `camera_capture` 任务 | `camera_task()` | 等帧 → 同步 cache → JPEG 编码 | 优先级 5，栈 8192 |
| `httpd` 任务 | `stream_handler()` 等 | 推 MJPEG 流 | **全服务器只有这一个任务**（见第 6 节限制） |
| `app_main` 主任务 | `app_main()` | 开机装配，装完就返回 | 返回 ≠ 程序结束，其它任务继续跑 |

### 两块通信设施

- `s_completed_frames`（FreeRTOS 队列）：**中断 → 任务** 传「哪块缓冲区拍满了」。中断里不能阻塞，
  所以用队列这个非阻塞通道。
- `s_frame_mutex`（互斥锁）：**编码任务 ↔ HTTP 任务** 之间保护 `s_jpeg_buffer / s_jpeg_size / s_frame_number`
  这一组共享数据。

```
上电
 └─ ESP-IDF 启动 → 初始化 PSRAM、堆、FreeRTOS → 调用 app_main()
     │
     ├─ ① nvs_flash_init()                 // Wi-Fi 驱动要存校准数据
     │
     ├─ ② initialize_camera()              // 8 步，见第 4.3 节
     │     ├─ LDO 通道 3 输出 2.5V          → 给 MIPI PHY 供电
     │     ├─ example_sensor_init()         → 通过 SCCB(I2C) 探测并配置 OV5647
     │     ├─ esp_cam_new_csi_ctlr()        → 建 CSI 控制器
     │     ├─ 分配 2 块 PSRAM 缓冲 + 队列
     │     ├─ 注册两个中断回调
     │     ├─ esp_cam_ctlr_enable()
     │     ├─ 建 ISP：RAW8 → RGB565
     │     ├─ 建 JPEG 编码器 + 输出缓冲
     │     └─ esp_cam_ctlr_start()          → 摄像头开始出图（中断开始刷）
     │
     ├─ ③ xSemaphoreCreateMutex() + xTaskCreate(camera_task, 栈8192, 优先级5)
     │     └─ 从这一刻起：帧不断被拍、被编码，s_frame_number 持续递增
     │

     │     └─ esp_wifi_init/set_mode(AP)/set_config/start()       ← 热点起来
     │
     ├─ ⑤ start_http_server()              // 必须在网络就绪之后

     │
```

## 4. 代码逐模块精讲

（本节是纲要与要点；**逐行的详细注释在 `annotated/main/main.cpp` 里**，建议对照阅读。）

### 4.1 常量与全局状态（`main.cpp` 第 32~53 行）

- `kWidth=800 / kHeight=640 / kRawFrameBytes = 800*640*2`
  **为什么乘 2 而不是 RAW8 直觉上的 ×1？** 两个原因叠加：
  1. CSI 输出端以 16 位为单位搬运 RAW8 像素；
  2. 更要紧的是 ISP 转换后的 RGB565 正好是 2 字节/像素。
  于是**同一块缓冲区前半程装 RAW8、后半程装 RGB565，大小刚好够用**——这就是 ISP 能「原地转换」、
  不必再开一块 RGB 缓冲的根本原因。理解了这点，你就理解了 `kRawFrameBytes` 为什么同时被用作
  CSI 缓冲区大小、`esp_cache_msync` 长度和 JPEG 编码输入长度。
- `kJpegBufferBytes = kRawFrameBytes + 64*1024`：JPEG 是变长压缩，留点余量避免极端画面下失败。
- `kCaptureBufferCount = 2`：双缓冲，防撕裂（见 5.1）。
- 全局变量用 `s_` 前缀、常量用 `k` 前缀，是 C++ 常见约定（Google 风格）。

### 4.2 两个中断回调（第 55~73 行）

```cpp
bool IRAM_ATTR camera_get_buffer(...)        // 硬件要下一帧的缓冲区
bool IRAM_ATTR camera_trans_finished(...)    // 一帧拍完了
```

要点：
1. **`IRAM_ATTR` 不是可选装饰**。中断上下文运行时，如果 flash 的 cache 正被别人占用，
   从 flash 取指的代码就会崩溃。加这个宏是把函数放进内部 RAM，保证随时可执行。
2. **回调里只做最少的事**：`camera_get_buffer` 交出 `s_capture_buffers[i]` 并轮换下标；
   `camera_trans_finished` 把指针 `xQueueSendFromISR` 丢进队列。绝不在这里做编码、`memcpy` 大块数据或打印日志。
3. **返回值有含义**：返回 `pdTRUE`/`true` 表示「我唤醒了更高优先级任务，请在退出中断时立刻切换上下文」。
   `camera_get_buffer` 固定返回 `false`（它没唤醒任何任务）；`camera_trans_finished` 返回
   `high_task_woken == pdTRUE`，让 `camera_task` 尽快开跑。
4. **队列满就丢帧，不阻塞**。中断被卡住会让整个系统失速，丢一帧只是画面轻微顿一下，这是正确的取舍。

### 4.3 `initialize_camera()`：8 步（第 75~153 行）

| 步 | 调用 | 作用 | 不做会怎样 |
|---|---|---|---|
| ① | `esp_ldo_acquire_channel()` | LDO 通道 3 输出 2.5V，给 MIPI PHY 供电 | 传感器能配置成功，但**一帧都收不到** |
| ② | `example_sensor_init()` | SCCB 探测型号、灌入寄存器配置 | 拿不到 `sccb_handle`，返回 `ESP_ERR_NOT_FOUND` |
| ③ | `esp_cam_new_csi_ctlr()` | 建 CSI 控制器 | 无法接收 MIPI 数据 |
| ④ | `esp_cam_ctlr_alloc_buffer()` ×2 + `xQueueCreate()` | PSRAM 里 2 块帧缓冲 + 交接队列 | 硬件无处可写 |
| ⑤ | `esp_cam_ctlr_register_event_callbacks()` | 挂上两个中断回调 | 拿不到帧 |
| ⑥ | `esp_cam_ctlr_enable()` | 控制器使能（还没开始拍） | `start()` 会失败 |
| ⑦ | `esp_isp_new_processor()` + `esp_isp_enable()` | RAW8 → RGB565 | 输出的是无法直接看的拜耳原始数据 |
| ⑧ | `jpeg_new_encoder_engine()` + `jpeg_alloc_encoder_mem()` | 建编码器与输出缓冲 | 无法压缩 |
| ⑨ | `esp_cam_ctlr_start()` | 真正开始出图 | 前面全白做 |

三个特别值得记住的细节：
- **缓冲区必须用 `esp_cam_ctlr_alloc_buffer()`**，不能随手 `malloc`：摄像头驱动对对齐方式和
  cache 属性有额外要求。且必须带 `MALLOC_CAP_DMA | MALLOC_CAP_SPIRAM`
  （DMA 能访问 + 放得下 1MB）。
- **CSI 的 `output_data_color_type` 故意保持 `CAM_CTLR_COLOR_RAW8`**（不是 RGB565）。
  原代码注释说明：ESP32-P4 revision v1.x 的 CSI 桥不支持颜色转换，必须 RAW8 直通，交给 ISP 干。
- **ISP 没传缓冲区参数**：因为它的输入和输出是同一块帧缓冲（原地转换），省掉一次 1MB 的大拷贝。

### 4.4 `camera_task()`：消费者（第 155~192 行）

```
xQueueReceive(portMAX_DELAY)          ← 没帧就让出 CPU，不空转
    ↓
esp_cache_msync(..., DIR_M2C)         ← ★ 最容易漏的一行
    ↓
xSemaphoreTake(s_frame_mutex, 200ms)
    ↓
jpeg_encoder_process(...)             ← 硬件编码
    ↓
s_jpeg_size = encoded_size; ++s_frame_number;   ← 顺序重要：先数据后帧号
    ↓
xSemaphoreGive(s_frame_mutex)
```

- **`esp_cache_msync` 为什么必须有**：帧缓冲在 PSRAM，而 P4 有数据缓存。DMA 是**绕过 cache
  直接写 PSRAM** 的，所以 CPU 的 cache 里可能还是上一帧的旧数据。`DIR_M2C`（memory→cache）
  让相关 cache 行失效，逼 CPU 重新从 PSRAM 读取。漏掉它的典型症状是**画面卡住不动**或
  **花花绿绿的错乱条纹**。
- **锁超时 200ms 的含义**：宁可放弃这一帧，也不死等导致整条采集流水线停摆。
- **先写 `s_jpeg_size` 再写 `s_frame_number`**：HTTP 端用「帧号变了」判断有没有新帧，
  顺序反了会读到半成品。

### 4.5 HTTP 层（第 194~291 行）

**`index_handler`（`GET /`）**：返回一段极简 HTML，页面里只有 `<img src='/stream'>`。
妙处在于**不需要任何 JavaScript**——浏览器自己会把 MJPEG 响应当「动图」持续刷新。

**`stream_handler`（`GET /stream`）**：整个项目的对外出口。MJPEG 协议原理：

```
HTTP/1.1 200 OK
Content-Type: multipart/x-mixed-replace; boundary=frame

--frame
Content-Type: image/jpeg
Content-Length: 23456
<JPEG 二进制数据>
--frame
Content-Type: image/jpeg
Content-Length: 23101
<JPEG 二进制数据>
   … 永不结束，直到客户端断开
```

`multipart/x-mixed-replace` 的语义是：「这是一个持续替换上一部分的多部分文档」。
浏览器每收到一部分就替换显示 → 不需要 JS、不需要 WebSocket 就是视频。

**这里有一个非常精妙的设计，值得单独学**：
```cpp
xSemaphoreTake(s_frame_mutex, 1000ms);
    memcpy(frame_copy, s_jpeg_buffer, jpeg_size);   // 持锁只做一次快速拷贝
xSemaphoreGive(s_frame_mutex);
... 不持锁地慢慢发网络 ...
```
为什么要多一块 `frame_copy`（每个客户端额外 1MB PSRAM）？因为网络发送很慢（可能几十毫秒甚至
几百毫秒），而编码任务在不停地覆盖 `s_jpeg_buffer`。如果**一边持锁一边发网络**，编码任务就得
等网络，整体帧率被网络拖死。正确做法是「持锁瞬间把当前帧偷出来，放锁后再慢慢发」——
**让慢操作（网络）和实时性要求高的操作（编码）互不阻塞**。这是实时系统里极常见的模式。

另外三个细节：
- 用 `httpd_resp_send_chunk()` 而不是一次性 `send`：流永不结束，**根本算不出 Content-Length**。
- `last_frame` 去重：没有新帧就不重复发，避免浪费内存带宽。
- 没有新帧时 `vTaskDelay(30ms)`：一定要主动让出 CPU，不能忙等。

**`start_http_server`**：先用 `HTTPD_DEFAULT_CONFIG()` 再覆盖三处。
默认值参考（来自 `esp_http_server.h`）：栈 4096、优先级 空闲+5、`max_open_sockets` 7、
`max_uri_handlers` 8。本工程把栈提到 8192（handler 里有 `snprintf`、日志、库内部调用）。

### 4.6 `start_wifi_ap()`：让没有 Wi-Fi 的 P4 拥有 Wi-Fi（第 293~340 行）

**这是本项目技术含量最高、也最容易被忽略的一段。** ESP32-P4 芯片内部**没有 Wi-Fi 射频**。
开发板上另有一颗 ESP32-C6，通过 SDIO 与 P4 相连。软件上要先用 **ESP-Hosted** 把这条链路
建立起来，P4 才能「像用本地 Wi-Fi 一样」调用 `esp_wifi_*`——这些调用会被自动转发给 C6。
配合 `main/idf_component.yml` 里的 `esp_wifi_remote` + `esp_hosted`，写代码的人几乎感觉不到差别。

函数内部分三步：
1. `esp_netif_init()` + `esp_event_loop_create_default()` + `esp_netif_create_default_wifi_ap()`
   —— 把 Wi-Fi 驱动和 TCP/IP 栈粘起来；默认 AP 会自动获得 **192.168.4.1** 这个地址
   （手机要访问的 IP 就来自这里，不是自己写死的）。注意这里**容忍 `ESP_ERR_INVALID_STATE`**，
   让函数可重复调用而不出错。
2. `esp_hosted_init()` → `esp_hosted_connect_to_slave()` —— **顺序不能反**。
   若日志停在 "ESP-Hosted C6 connection failed"，多半是 C6 里没烧录对应的 hosted slave 固件。
3. `esp_wifi_init/set_mode/set_config/start` —— 起热点。这里的错误处理**换成了
   `ESP_ERROR_CHECK`**（失败即 panic 并打印调用栈），因为这类「错了就没意义」的配置错误
   应该立刻暴露，而不是悄悄返回。

对比着看，你能学到**错误处理分三档**的工程习惯（见 5.8）。

### 4.7 `app_main()`：开机装配（第 344~375 行）

顺序不能乱：**NVS → 摄像头 → 任务 → Wi-Fi → HTTP**。
- HTTP 服务器必须绑定在已存在的网络接口上，所以**先起 Wi-Fi 再起 HTTP**。
- `app_main` 最后**返回**了，但程序没结束：`camera_task` 和 `httpd` 任务仍在后台运行。
  「入口函数结束 ≠ 程序结束」是嵌入式里的常见形态，初学者容易困惑。
- `extern "C"` 不能省：IDF 启动代码用 C 编译，按 C 的名字修饰查找 `app_main`。

## 5. 十个值得学的设计决策（含各自代价）

学一个项目，最有效的不是背 API，而是问「他为什么这么写？换一种写法会怎样？」

| # | 决策 | 好处 | 代价 / 局限 |
|---|---|---|---|
| 1 | **双缓冲 ping-pong** | DMA 拍 A 时 CPU 处理 B，避免撕裂 | 只 2 块，编码跟不上采集时仍会被覆盖（见第 6 节） |
| 2 | **中断只投递、不做重活**（队列 + `FromISR`） | 中断极短，系统实时性好 | 队列满时静默丢帧 |
| 3 | **`esp_cache_msync(DIR_M2C)`** | 保证 CPU 读到 DMA 新写的 PSRAM 数据 | 每帧一次同步有开销；漏写会花屏/卡死 |
| 4 | **ISP 原地转换** | 省一块 1MB RGB 缓冲和一次大拷贝 | 牺牲了「保留原始 RAW」的可能 |
| 5 | **持锁只做 memcpy，网络不持锁** | 网络再慢也不拖累编码帧率 | 每个客户端多占 1MB PSRAM |
| 6 | **用「帧号变化」判断新帧** | 免去条件变量，逻辑简单可靠 | 依赖「先写 size 再写 number」的写序约定 |
| 7 | **配置与逻辑分离**（`example_config.h`、`sdkconfig.defaults`） | 换板子/换分辨率只改配置 | 同一个值在多处重复（分辨率要改 3 处） |
| 8 | **错误处理分三档** | 见下 | 需要判断力：哪些该 panic，哪些该降级 |
| 9 | **日志节流**（第 1 帧 + 每 100 帧） | 不刷屏、不拖慢串口 | 丢失细节，排错时可能想临时调密 |
| 10 | **借用外置 Wi-Fi（ESP-Hosted）** | P4 也能上网，API 与本地 Wi-Fi 一致 | 多一颗芯片、多一层固件、多一类故障点 |

**第 8 条展开——三档错误处理（这是工程素养，不是 API 知识）**：
1. `ESP_RETURN_ON_ERROR(...)`：**可恢复**的初始化失败 → 记日志并返回，让调用者决定（本工程大量使用）。
2. `ESP_ERROR_CHECK(...)`：**配置类、错了就没意义**的失败 → 直接 panic + 打印调用栈，便于定位。
3. `ESP_LOGE` + `return`：**需要给人看明白的失败**（如「没检测到摄像头」）→ 给出可操作的错误信息。

## 6. 已知局限与改进方向（带着这些问题学，进步最快）

| 局限 | 现状 | 怎么改 |
|---|---|---|
| **只能一个观众** | ESP-IDF HTTP 服务器**只有唯一一个 `httpd` 任务**，用 `select()` 轮询后**依次**调用处理函数；`stream_handler` 在连接期间一直不返回，就把这个任务独占了。第二个设备访问会一直转圈 | 改用异步 handler（`httpd_req_async_handler_begin()`），或换 RTSP/WebSocket |
| **可能撕裂** | 只有 2 块缓冲，且 `camera_get_buffer` 立即交出下一块，不等消费者用完；编码慢于采集时会被覆盖 | 加到 3~4 块缓冲；或让消费者归还缓冲区后再取 |
| **参数写死** | 分辨率、质量 70、亮度、热点密码全在编译期常量里 | 加 HTTP 接口（`/config?quality=50`）或存 NVS |
| **密码硬编码** | `kApPassword = "p4camera8"` 明文写在源码里（README 已提醒部署前修改） | 存 NVS，或用配网流程 |
| **无断连检测之外的健壮性** | 靠 `httpd_resp_send_chunk` 报错才发现客户端走了 | 加心跳/超时；同时给任务加看门狗 |
| **不需要的载荷** | 客户端断开后要等下一次发送失败才知道，期间 `frame_copy` 一直占着 1MB | 缩短发送超时；及时释放 |
| **没有抓拍/录像** | 只能看实时流 | 加 `GET /capture` 返回单帧 JPEG；写 SD 卡 |
| **没有 OTA** | 升级要插线 | 启用 `esp_https_ota` + 分区表调整 |

**建议的学习姿势**：不要一上来就重写。先按第 8 节把项目**跑通并复刻**，再挑上表里的一项动手改，
每改一项都对照第 5 节思考「我的改动动了哪个权衡」。

## 7. 从零到能写出它：分阶段学习路线

> 假设你**已经会 C 语言基础**（变量、循环、函数、指针、结构体）。若不会，先在 PC 上补 C 语言，
> 再回来。全程约 4~8 周（每天 2~3 小时）；有单片机经验可压缩到 2~3 周。
>
> 每个阶段都给了「看哪个官方例程（本机真实路径）」和「动手练习」，**练完再进下一阶段**。
> `$IDF_PATH` 在本机 = `D:\ESP_IDF\v6.1\esp-idf`。

### 阶段 0：C / C++ 基础（约 3~5 天）

| 要掌握 | 为什么这个项目需要它 |
|---|---|
| 指针、数组、`void *`、类型转换 | 帧缓冲区就是 `void *`，到处在 `static_cast` |
| 结构体与初始化 | 所有 `*_config_t` 都是结构体，**未清空 = 随机值 = 玄学 bug** |
| `constexpr`、`namespace`、`static_cast`、`reinterpret_cast` | `main.cpp` 里的常量、匿名命名空间、各种 cast |
| 位运算、字节序概念 | RAW8/RGB565 打包、`PRIu32` 格式化 |
| 宏与条件编译 | `ESP_RETURN_ON_ERROR`、`IRAM_ATTR`、`#pragma once` |

**重要习惯**：本项目所有 config 结构体都写成 `esp_xxx_config_t cfg = {};`——
这个 `{}` 把整个结构体清零。**漏掉它，未显式赋值的字段就是栈上的垃圾值**，
这类 bug 极难查。看到 `= {}` 就要意识到「这是在清空，很重要」。

练习：写一个 PC 端小程序，用 `struct` + 指针 + 函数指针，模拟「生产者-消费者」两个线程。

### 阶段 1：ESP-IDF 构建体系与工具链（约 2~3 天）

要掌握：`idf.py set-target/build/flash/monitor/menuconfig`、工程目录结构、
**组件（component）概念**、`idf_component_register` 的 `SRCS/INCLUDE_DIRS/REQUIRES`、
`Kconfig` 与 `sdkconfig`、分区表、组件管理器（`idf_component.yml` + `dependencies.lock`）。

看例程（本机路径）：
- `$IDF_PATH/examples/get-started/hello_world` —— 最小工程，看它的 CMakeLists
- `$IDF_PATH/examples/get-started/blink` —— 加上了 `sdkconfig.defaults`

**最容易卡住的一点**：ESP-IDF 里 `#include` 一个头文件，必须同时在 `CMakeLists.txt` 的
`REQUIRES` 里写上对应组件名，否则编译报 `No such file or directory`。这跟「系统头文件随便 include」
的心智完全不同。

练习：把本工程 `main/CMakeLists.txt` 里的 `REQUIRES` 随便删掉一个（如 `esp_driver_jpeg`），
观察报错信息，再改回来。**亲手制造一次错误，比读十遍文档管用。**

### 阶段 2：FreeRTOS（约 3~5 天）

要掌握：任务（`xTaskCreate` 的每个参数含义）、优先级与抢占、`vTaskDelay`、
队列（`xQueueCreate/Send/Receive`）、**ISR 安全版本**（`xQueueSendFromISR` + `xHigherPriorityTaskWoken`）、
信号量/互斥锁、栈溢出排查。

看例程：`$IDF_PATH/examples/system/freertos/basic_freertos_smp_usage`、
`$IDF_PATH/examples/system/freertos/real_time_stats`

**必须自己回答的三个问题**（回答不了就回去继续读）：
1. 为什么中断里要用 `xQueueSendFromISR` 而不是 `xQueueSend`？
2. `portMAX_DELAY` 是什么意思？在中断里能用吗？（不能）
3. 本工程为什么把 `camera_task` 设成优先级 5、栈 8192？改小会怎样？
   （栈小 → 溢出崩溃，可用 `uxTaskGetStackHighWaterMark` 量出来）

### 阶段 3：内存、DMA 与 cache 一致性（约 2~3 天）

这是**从「能点亮 LED」跨到「能处理图像」的关键一步**，也是初学者最大的坎。

要掌握：内部 SRAM vs **PSRAM** 的差别；`heap_caps_malloc` 按能力分配
（`MALLOC_CAP_DMA` / `MALLOC_CAP_SPIRAM` / `MALLOC_CAP_8BIT`）；**DMA 绕过 cache** 的事实；
`esp_cache_msync` 的两个方向（`DIR_M2C` 失效 cache 以读新数据、`DIR_C2M` 回写以便硬件读）；
`psram` 相关 `menuconfig` 选项。

练习：
1. 用 `heap_caps_get_free_size(MALLOC_CAP_SPIRAM)` 在串口打印 PSRAM 余量，
   在本工程里加一句日志，看开机后掉了多少内存（能直观看到 4.2MB 去哪了）。
2. 在 PC 上想清楚这个问题：如果 cache 命中，CPU 读哪个值？（一个具体例子：
   DMA 把 0x12345678 写进 PSRAM，而 cache 里还缓存着 0xAAAAAAAA——CPU 读到的会是哪个？）

### 阶段 4：GPIO 与 I2C（约 2 天）

要掌握：GPIO 输入输出、I2C 主机 API（`i2c_new_master_bus` / `i2c_master_transmit` 等）、
用逻辑分析仪或示波器看 I2C 波形、**SCCB 与 I2C 的关系**（SCCB 是 OV 摄像头的控制总线，
电气兼容 I2C，所以直接用 I2C 主机驱动）。

看例程：`$IDF_PATH/examples/peripherals/gpio/generic_gpio`、
`$IDF_PATH/examples/peripherals/i2c/i2c_basic`、`$IDF_PATH/examples/peripherals/i2c/i2c_tools`

练习：用 `i2c_tools` 例程扫 I2C 总线，确认能看到 OV5647 的地址（通常是 0x36）。
**这一步是排查「摄像头探测失败」最直接的证据**：扫不到地址 → 接线/供电/上拉电阻问题；
扫得到但初始化失败 → 格式名或型号问题。

### 阶段 5：摄像头链路 MIPI-CSI + ISP（约 3~5 天）

**这是本项目最专的部分，也是唯一必须看例程源码的地方。**

要掌握：
- **DVP vs MIPI-CSI** 两种摄像头接口的区别（并口 vs 差分串行）
- 传感器输出格式的含义：`RAW8`（拜耳原始）、`RGB565`、分辨率、lane 数、输入时钟、
  lane bitrate、fps —— 这些信息全都在格式名里
- CSI 控制器：`esp_cam_new_csi_ctlr` + 中断回调 + `esp_cam_ctlr_alloc_buffer` 的缓冲区模型
- ISP：为什么 RAW 不能直接看、去马赛克是什么、`esp_isp_new_processor`
- 组件的分工：`esp_cam_sensor`（传感器驱动 + 寄存器表）、`esp_sccb_intf`（控制总线抽象）、
  `sensor_init`（自动探测封装）

**必看例程（与本工程结构几乎一一对应，是最好的老师）**：
```
$IDF_PATH/examples/peripherals/camera/mipi_isp_dsi/main/mipi_isp_dsi_main.c
```
对照阅读你会发现：LDO 供电、`example_sensor_init`、`esp_cam_new_csi_ctlr`、两个中断回调、
`esp_isp_new_processor`、`esp_cache_msync` 的写法几乎一模一样。**本工程就是把
「CSI + ISP 输出到 DSI 屏」这条链路的末端，从「屏幕」换成了「JPEG + HTTP」。**
看懂这个例程，你就看懂了这个项目的主干。

配套看：
- `$IDF_PATH/examples/peripherals/camera/mipi_isp_dsi/main/example_config.h` —— 格式名与引脚的写法
- `$IDF_PATH/examples/peripherals/camera/common_components/sensor_init/` —— 自动探测怎么实现
- `$IDF_PATH/examples/peripherals/camera/dvp_isp_dsi/` —— 对照理解 DVP 与 MIPI 的差异
- `$IDF_PATH/examples/peripherals/isp/multi_pipelines/` —— 理解 ISP 的更多能力

练习：把本工程的分辨率改成 800×800（格式名、`kWidth/kHeight`、
`sdkconfig.defaults` 里的 `CONFIG_CAMERA_OV5647_MIPI_RAW8_800X800_50FPS` 三处联动改），
感受「分辨率贯穿了整条流水线」。

### 阶段 6：JPEG 硬件编码（约 1~2 天）

要掌握：`jpeg_new_encoder_engine`、`jpeg_alloc_encoder_mem`（注意它会回写实际容量）、
`jpeg_encoder_process`、质量参数与色度子采样（YUV422 vs YUV420）对画质/体积的影响。

看例程：`$IDF_PATH/examples/peripherals/jpeg/jpeg_encode`

练习：把 `image_quality` 从 70 分别改成 30 / 90，观察日志里 `jpeg=xxxxx bytes` 的变化，
并对比手机上的画质。**亲手验证「质量 ↔ 体积 ↔ 帧率」的三角权衡。**

### 阶段 7：网络：netif + Wi-Fi + ESP-Hosted（约 3~4 天）

要掌握：`esp_netif`（为什么 Wi-Fi 和 TCP/IP 之间需要它）、默认事件循环、
SoftAP 模式、`wifi_config_t` 各字段、AP 的默认 IP 是 192.168.4.1 这件事从哪来。

看例程：`$IDF_PATH/examples/wifi/getting_started/softap` —— **先把它在普通 ESP32 上跑通**，
理解「标准 SoftAP 流程」长什么样。

然后理解本项目与之的**关键差异**：P4 没有 Wi-Fi 射频，所以多了 `esp_hosted_init()` +
`esp_hosted_connect_to_slave()` 两步，并把 `esp_wifi_init` 提前到 netif 之后。
好消息是 `esp_wifi_remote` 让 `esp_wifi_*` 的 API 签名与本地 Wi-Fi 完全一致，
所以你先按「标准 SoftAP」学会写，再看这多出来的两步，就很容易理解。

补充阅读：`managed_components/espressif__esp_hosted/` 里的 README 与文档，
了解 P4 与 C6 之间的传输方式（SDIO）和 C6 侧需要烧录的 slave 固件。

练习：把热点 `channel` 从 6 改成 1 或 11，重新测速；查一下为什么「1/6/11」被称为
2.4GHz 的三个不重叠信道。

### 阶段 8：HTTP 服务器、MJPEG 与流式传输（约 2~3 天）

要掌握：`httpd_start`、`httpd_uri_t` 注册路由、`httpd_resp_send` vs `httpd_resp_send_chunk`、
HTTP 响应头、**分块传输编码（chunked）**、**multipart/x-mixed-replace**、
以及「为什么 MJPEG 不需要 JS」。

看例程：
- `$IDF_PATH/examples/protocols/http_server/simple` —— 最小 HTTP 服务器
- `$IDF_PATH/examples/protocols/http_server/file_serving` —— 发文件（对照「单次完整响应」怎么写）
- `$IDF_PATH/examples/protocols/http_server/async_handlers` —— **进阶**：想让多人同时看时要学的那个

**必须理解的一点**：本项目用 `multipart/x-mixed-replace` 而不是造一个私有协议，
是因为**浏览器原生支持**——`<img src="/stream">` 就能播，不用写一行 JS。
这是「用现有标准解决新问题」的典型工程智慧。

练习：用电脑浏览器打开开发者工具（F12）→ Network → 点开 `/stream`，
**亲眼看那个永不结束的响应体**，找到 `--frame` 边界和 `Content-Length`。
看一次，比读十遍 MJPEG 定义都清楚。

### 阶段 9：调试与排错（约 2 天，贯穿始终）

要掌握：
- 日志分级与 `ESP_LOGI/W/E`，以及 `TAG` 的作用
- `esp_err_to_name()` 把错误码变成人话
- **`ESP_ERROR_CHECK` 崩溃后怎么读回溯**（`idf.py monitor` 会自动解析地址为函数名）
- `idf.py size` / `size-components` 看空间占用
- `heap_caps_print_heap_info()` 看内存碎片
- `idf.py monitor` 的快捷键（Ctrl+] 退出）
- **`idf.py monitor` + `esp_task_wdt`** 排查「任务卡死」

练习：故意在 `stream_handler` 里删掉 `free(frame_copy)`，连几次流，用
`heap_caps_get_free_size(MALLOC_CAP_SPIRAM)` 打印观察内存一路下降——**亲手复现一次内存泄漏**，
以后就再也不会忘了这对 `malloc/free`。

## 8. 复刻路线：8 个可验证的里程碑

不要试图一次写完 375 行。按下面**每步都能独立验证**的顺序做，每步都在开发板上看到结果再往下走。
这样出错时你永远知道是「刚加的那一段」有问题。

| 里程碑 | 做什么 | 验收标准 | 对应本工程 |
|---|---|---|---|
| **M1** | `hello_world` 跑通：串口打印 + 能烧录 | 串口看到循环打印 | 环境搭建 |
| **M2** | 用 I2C 扫描，找到摄像头地址 | 串口打印出 0x36 之类的地址 | 对应 `initialize_camera()` 第①②步 |
| **M3** | 初始化传感器 + CSI，**只打印「收到一帧，大小 N 字节」** | 串口持续打印帧大小 | `camera_get_buffer` / `camera_trans_finished` / 队列 |
| **M4** | 加上 ISP，把一帧编码成 JPEG，打印 JPEG 大小 | 打印出合理的 JPEG 尺寸 | ISP 部分 + `jpeg_encoder_process` |
| **M5** | 起 SoftAP，手机能连上并拿到 IP | 手机显示已连接 | `start_wifi_ap()` 前半 |
| **M6** | 加 HTTP，**`GET /capture` 返回一张静态 JPEG** | 手机浏览器能显示一帧图片 | `start_http_server` + 文件式响应 |
| **M7** | 把 `/capture` 改成 `/stream` 的 MJPEG 循环 | 手机看到连续画面 | `stream_handler` 全部 |
| **M8** | 优化：双缓冲、`esp_cache_msync`、锁与拷贝分离 | 画面不撕裂、帧率稳定 | 本工程最终形态 |

**M3 是本项目真正的分水岭**：能稳定拿到帧，后面就都是「数据的搬运与变换」了。
如果 M3 卡住，问题通常只有三类——**LDO 供电、SCCB 接线/地址、格式名不匹配**，
按这个顺序查。

## 9. 排错手册

| 症状 | 最可能的原因 | 怎么查 |
|---|---|---|
| 日志 `No supported MIPI camera was detected` | ① 型号不支持 ② SCCB 接线错 ③ 格式名不匹配 | 先跑 I2C 扫描确认地址；再核对 `EXAMPLE_CAM_FORMAT` 与 `sdkconfig.defaults` 里的 `CONFIG_CAMERA_OV5647_*` |
| CSI 起来了但一帧都没有 | MIPI PHY 没供电 | 检查 `esp_ldo_acquire_channel`（通道 3、2.5V）是否执行成功 |
| 画面花屏、条纹、卡住不动 | **漏了 `esp_cache_msync`** | 确认 `camera_task` 里那行 `DIR_M2C` 存在 |
| 画面上下撕裂 | 缓冲不够 / 编码慢于采集 | 加缓冲数量；降分辨率或质量 |
| 分配缓冲区失败（NO_MEM） | PSRAM 没开或模式不对 | 查 `CONFIG_SPIRAM`、`CONFIG_SPIRAM_MODE_HEX`；用 `heap_caps_get_free_size(MALLOC_CAP_SPIRAM)` 打印 |
| `ESP-Hosted C6 connection failed` | C6 里没烧录 hosted slave 固件；或 SDIO 配置不符 | 见 `managed_components/espressif__esp_hosted` 文档；确认 C6 固件已烧 |
| 手机连不上热点 | SSID/密码/信道问题；密码不足 8 位 | 密码 < 8 位必须把 `authmode` 改成 `WIFI_AUTH_OPEN` |
| 手机打开网址转圈没反应 | **已被另一个客户端占住唯一的 httpd 任务** | 关掉其它正在看的设备；或改异步方案（第 6 节） |
| 编译报 `xxx.h: No such file or directory` | 忘在 `main/CMakeLists.txt` 的 `REQUIRES` 里加组件 | 对照第 4 节的组件清单 |
| 帧率低 | JPEG 质量过高、分辨率过高、PSRAM 带宽不足 | 先降 `image_quality`，再降分辨率；`CONFIG_SPIRAM_SPEED_200M` 要开 |
| 看一会儿就断流 | 内存泄漏 / 看门狗 | 查 `free(frame_copy)`；开 `esp_task_wdt` 看哪个任务卡住 |
